# Linux live-camera acceptance ? 2026-10-24

## Outcome

A working Linux pilot is deployed at **http://187.127.189.231:21000/** under
`/home/mohan/cam`, user `mohan`. Windows v2 was left running and its source was not
modified. The receiver and Node server now run in a restartable bounded container.

## Root cause of the earlier Linux failure

The original DLL subset omitted dynamically loaded components: DataCenterApi.dll,
NetStream.dll, SystemTransform.dll, ezMobileSDK.dll and their dependencies. A Wine
file trace exposed missing runtime lookups that a normal PE import scan did not
show. Adding the installed client's files fixed the device authorization call:
result 0, SDK error 0, 3317 response bytes. The same grant passed on Windows.

A separate libcurl control found that the library's generic public-root HTTPS
request needs an explicit CA bundle in Wine. An in-process diagnostic hook tested
that possibility with peer/hostname verification enabled. The production SDK path
works without that hook after the missing dependencies were installed. No SDK
binaries were modified, and no TLS verification bypass is used in the receiver.

## Measurements and acceptance evidence

- All five recorders were online initially (48 shared channels). A first channel
  on every recorder eventually played; KPM 3 required a retry.
- A private short SD capture was decoded by FFmpeg: H.265, 352?288, reported 25fps,
  47 decoded frames. The temporary capture is removed after verification.
- Continuous SDK/PyAV reception produced compressed H.264 and non-silent PCM:
  one initial interval measured 26.5 output fps. Other cameras/intervals differ.
- HD decoded successfully: KPM 5 at 960?1088, KPM 2 at 1280?720. Observed HD output
  on this constrained VPS was about 9?12fps; 30fps HD is not established.
- Four concurrent KPM 5 SD channels played. Stop and reconnect passed.
- The final shared SDK receiver displayed **eight KPM 3 cameras simultaneously**
  in the public HTTP website. All eight canvases advanced over a five-second check.
  Example simultaneous output intervals were 4.7?11.3fps under the resource cap;
  this establishes function, not full-frame-rate capacity.
- HTTP browser playback passed using MediaSource / fragmented MP4 with no
  WebCodecs dependency. One continuous browser check painted 1065 frames with
  zero decoder errors. Approximately 900ms of buffering is retained, and excessive
  buffered latency is bounded.
- Audio packets arrived on KPM 5 and KPM 3 microphone channels. A private receiver
  sample contained 121600 PCM samples with nonzero RMS (10261.4). Some other
  channels, including tested KPM 2 channel 1 HD and SD, exposed no audio in that
  media stream. No claim is made that all 48 channels have verified sound.
- Fresh decoded previews passed for every KPM 3 channel (8), every KPM 2 channel
  (16), and every KPM 1 channel (8): **32 successful channel preview checks**.
  KPM Bus 4 went offline during its sweep (one timeout, then offline rejections).
  KPM 5 was offline before the full sweep. Reports preserve failures rather than
  treating the cloud online flag as proof of playable video.
- Zoom selected the correct tile without enlarging it. A snapshot JPEG was created
  in memory (39634 bytes). Recording started/stopped and offered a clip; the test
  clip was removed without downloading. No test footage is retained as a deliverable.
- Container restart preserved the owner account and saved grant. Public health
  returned 200 after restart. Unauthenticated device APIs returned 401.
- Regression checks: 55 passed, 0 failed, 2 Windows-only checks skipped. Two
  additional Linux filesystem/socket checks passed. The Windows Python runtime also passed 6 synthetic audio tests and 4 smooth-video round-trip/timestamp tests (67 automated passes in total, plus 2 intentional Windows-only skips). The suite includes SDK pool
  routing isolation: same-grant streams share a process, other grants do not,
  and stopping one synthetic stream does not stop another.

## Limits / unfinished live acceptance

All five recorders subsequently became offline according to fresh Hik-Connect
responses. The last attempt to verify live rotation therefore could not complete.
The UI held the current batch and reported that the next cameras were not ready.
Actual SDK stop isolation also could not be checked at that point because there
was no online recorder. Synthetic pool isolation and existing rotation tests pass;
these do not replace the outstanding live rotation test.

This is a pilot. Plain HTTP transport, independent SDK login/renewal, Linux talk,
and sustained high-concurrency HD capacity still require work. Credentials are
saved, not made permanent: provider expiry and revocation still apply. No passwords,
SDK tokens, serials, raw cloud responses or pictures are included in this report.
